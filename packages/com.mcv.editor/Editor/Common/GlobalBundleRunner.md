# Contract: GlobalBundleRunner

Role: the single executor of the global-bundle AssetBundle pipeline: a global bundle is one bundle of shared assets with no ProjectClip (clipId empty), driven entirely by an IGlobalBundleProvider so that CameraBg / RoomOne / UI / Fonts differ only in "where the entries come from + what the bundle is called + three policies + which bundles must be built with it".

Methods:
Run(provider, build, interactive)  compile guard, collect, asset validation, stale-config sweep, write the configs, read-back self-check, sync PackageDB_Master, then (optionally) build the provider plus every bundled dependency in ONE BuildAssetBundles call; the global-bundle pipeline in one place
BundleDirName(bundleName)  private: first segment of the bundle name = the output directory under StreamingAssets; null for anything that is not exactly "dir/file"
Collect(provider)  private: run provider.Collect() and drop null entries and entries with an empty id
PlanBuild(bundleName, entries)  private: fold one bundle's entries into a single AssetBundleBuild (assetNames order preserved)
ResolveDependencies(provider, logTag)  private: the provider's BuildWith list, skipping nulls and empty bundle names and de-duplicating on bundle name (the main bundle is pre-seeded, so a dependency may not declare itself)
Validate(entries, abortOnFirst)  private: asset existence plus import type per entry.kind (Sprite to Texture2D + TextureImporter, Font / TmpFont to a main-asset null check, everything else to GameObject), then a duplicate-id check; returns the problem list
WithNote(entry, message)  private: append entry.note in parentheses to a problem message
HeadLines(lines, max)  private: join the first max lines and fold the rest into one "another N" line

Notes:
- Assets/Editor/Common is the shared kernel: this is the only global-bundle flow, never fork a second routine into the tools (the CameraBg / RoomOne tools used to repeat these eight segments almost line by line).
- Dependency direction stays one-way: this class only knows MCV_Module.Interfaces.IGlobalBundleProvider (runtime assembly) plus the Common kernel, while the providers live in Assets/Editor/BuildTools/GlobalProviders; Common must never reference BuildTools.
- Invariants: output directory = the bundle name's first segment; BundleBuilder is called with sweepStale:true; clipId is always written as null (a global bundle is resident and is never taken away by the per-clip load/unload path); the bundle name must be exactly "dir/file" with a lower-case file segment.
- The log tag is [{Name}AB] and the dialog title is "{Name} AB" (CameraBg / RoomOne keep their original tags and titles); interactive=false shows no dialog at all, which is the clean path for automation and MCP sessions.
- The runner owns the dialogs that the two tools used to own; interactive entries (menu items) keep them, non-interactive ones never reach them.
- The result count in the dialogs is generated.Count - broken.Count (configs actually written, minus the ones whose m_Script was lost), which equals the old per-tool numbers as long as config creation does not fail.
- Bundle-name failure, a null provider and an empty entry list are the runner's only new guards; the two existing tables are never empty, so they are unreachable for CameraBg / RoomOne.
- Reused as-is: EditorAssetUtil (IsScriptReady / DeleteAssetsNotIn / FindBrokenAssets), PackageConfigWriter (CreateOrUpdate / ApplyContent), PackageDatabaseSync.Sync, BundleBuilder.Build, EditorPaths.
- B3 added the Font / TmpFont branch to Validate and changed nothing else in the validation / config-writing phases: the two font shapes are two separate assets (UnityEngine.Font and TMPro.TMP_FontAsset), and the check is a plain AssetDatabase.LoadMainAssetAtPath null test. It deliberately does not name a TMPro type, so the shared kernel keeps depending on Interfaces + Models only (AGENT.md red line). Prefab still falls into the trailing else branch, so the CameraBg / RoomOne / UI validation semantics are byte-for-byte unchanged.
- The build phase is batched: the provider's own bundle plus every provider in its BuildWith list go into ONE BuildAssetBundles call, because Unity's "an asset explicitly assigned to a bundle is no longer copied" rule only holds within a single call. Measured: building the panel bundle and the font bundle separately gives a 6187 KB panel bundle with SIMHEI.TTF copied inside, while one call yields a 152 KB panel bundle plus a 6033 KB font bundle (dependency only). Menu items therefore still run only their own provider (Run(thisProvider, ...)) and the runner pulls the dependency in automatically; the font menu alone builds only the font bundle, which is correct because fonts depend on nothing.
- Every bundle in the batch lands in its own first-segment directory (UI/ui -> StreamingAssets/UI/, Fonts/font -> StreamingAssets/Fonts/) and the stale sweep runs per directory with only that directory's own bundle file names. Sweeping with the union of all bundle names would delete another pipeline's output; and copying only the main provider's bundle would leave a dependent bundle stale when only one menu is run.
- Dependency resolution is single-level: the batch is the provider itself plus its own BuildWith entries; the dependencies' own BuildWith lists are NOT walked transitively. That is sufficient for the current graph (UI -> Fonts, Fonts -> nothing) and keeps the batch free of cycles; a future bundle that needs a two-hop dependency must declare the intermediate bundle directly.
- Each provider still runs its own config phase (collect / validate / config sweep / write / DB sync) exactly as before; only the build call is shared. A dependency that collects no entries (e.g. the font catalog is not created yet) is skipped with a warning instead of aborting, so the main bundle still gets built.
- The pre-build confirm dialog and the log now name the whole batch ("本次同批构建：UI/ui + Fonts/font") plus the directories written, so a user running the UI menu can see the font bundle was rebuilt too.
